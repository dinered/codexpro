# Discussion sync

`plan.mjs` is the detailed read-only inventory/planner. It covers every current GitHub issue/PR and GitLab issue/MR, mapped comment candidates, inline discussions, review snapshots, state-copy candidates and unmapped counterpart proposals. It explicitly selects GitHub/GitLab API hosts, bounds API calls to 20 seconds and page scans to 100 pages, and emits hashes and metadata without comment bodies.

`sync.pl` is the Perl 5 + core `JSON::PP` execution path for the shared shell runner, which does not have Node. It writes only ordinary comments on existing mapped objects: the current authorized first backfill contains 19 candidates. It emits the complete informational counterpart, status-copy and unmapped-discussion proposal snapshots as read-only rows; it does not create issues/PRs/MRs, close objects, replay review votes, merge, or delete. The proposal snapshots are retained so the 19-comment plan cannot hide unmapped project history; refresh them from a reviewed live inventory before a later scope change.

The local commands use existing authenticated CLI helpers and never print token values:

```sh
node tools/discussion-sync/plan.mjs --github-cli /home/paseo/.local/bin/gh
perl tools/discussion-sync/sync.pl
perl tools/discussion-sync/core.test.pl
perl tools/discussion-sync/integration.test.pl
node --test tools/discussion-sync/plan.test.mjs
```

`sync.pl` defaults to read-only. It emits a SHA-256 plan hash bound to current mapped source body hashes, implementation code, mapping and proposal files. An apply requires `--apply`, `DISCUSSION_SYNC_ENABLED=true`, and a matching `DISCUSSION_SYNC_EXPECTED_PLAN_SHA256`. The CI job additionally runs only on protected `main` from a web or schedule pipeline, and is disabled unless `DISCUSSION_SYNC_ENABLED=true`; its default is `DISCUSSION_SYNC_APPLY=0`.

Before each create/revision, the writer re-fetches the exact source comment through its object-scoped API endpoint and verifies its body hash, re-reads target comments, and fails on malformed/edited target markers. Structured writes set `Content-Type: application/json`. It emits an attributed envelope with the original author, timestamp and permalink; the actual API actor remains the writer. A strict terminal marker containing forge/project/object/comment identity and source-body hash is the durable mapping/checkpoint. A valid marker prevents echo and makes retries after partial failure idempotent. Source edits create an attributed revision; target edits become conflicts. Attachments stay in manual review. A local lock plus GitLab `resource_group` serializes this writer's invocations; third-party writers do not participate in that lock.

CI uses `GH_TOKEN`/`GITLAB_TOKEN` process environment populated from existing `GITHUB_SYNC_TOKEN`/`GITLAB_SYNC_TOKEN`; credentials are not placed in argv or output. GitHub comment writes need repository-scoped **Issues: read/write** and **Pull requests: read/write**; GitLab notes need project API write access. Grants are not introspected and token values are never read. An authorized apply against a reviewed exact plan is the capability check; API 401/403 failures are sanitized and stop the run. Local runs continue to use the current `gh`/`glab` authentication helpers.

The CI job `discussion-sync-test` runs core and fake-CLI integration tests for marker validation, loop prevention, retries/revisions/conflicts, UTF-8 JSON transport, source and target revalidation, plan-hash rejection, missing-binary and 401/403 diagnostics, and lock exclusion without credentials or Node. These tests execute the actual `sync.pl` orchestration. `discussion-sync-cli-test` verifies the runner-local CLI bootstrap and installs the pinned official `gh` and `glab` releases into `.ci-tools/bin`; the protected deploy job uses the same bootstrap before contacting either API. No host-wide installation or credential login is performed. SHA-256 digests are pinned in `bootstrap-cli.sh` for Linux amd64/arm64 and checked before extraction. Node planner tests remain available locally for the exhaustive row planner.

The protected job wraps its command with `with-glab-protocol.sh`, which writes only the scoped `api_protocol` into a temporary `GLAB_CONFIG_DIR` (directory mode 700, config file mode 600) and removes it on exit. This is needed for pinned `glab` 1.103.0: its `api_protocol` default is HTTPS and the [v1.103.0 config schema](https://gitlab.com/gitlab-org/cli/-/blob/v1.103.0/internal/config/schema.go) has no environment-variable mapping, so setting the newer `GLAB_API_PROTOCOL` variable alone does not change the API URL. The pinned [API endpoint builder](https://gitlab.com/gitlab-org/cli/-/blob/v1.103.0/internal/glinstance/host.go) uses the selected protocol when forming self-managed API URLs. The wrapper takes the protocol from GitLab's predefined `CI_SERVER_PROTOCOL`; it does not read or modify global auth/config and does not put credentials in this temporary file. `glab-protocol.test.pl` checks the pinned binary's resolved scheme from an isolated config with credential environment variables removed and telemetry/update checks disabled.
