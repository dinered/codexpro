# Учебная реализация и боевая: в чём разница

Документ для разбора с учениками. Здесь собрано всё, чем учебный codexpro
(плагин Paseo, мост в ChattyMy, песочницы, синхронизация с GitHub) отличается
от того, как такую же задачу решали бы в боевой системе. Для каждого отличия:
как сделано сейчас, как было бы в бою, почему в учебном сделано так и чем это
грозит.

Проект учебный (`AGENTS.md`), и «боевое» здесь — не план проекта, а образец для
сравнения: что пришлось бы поменять, если бы ту
же задачу решали всерьёз.

## Как читать и как искать в коде

Каждое отличие помечено меткой `#учебно-не-боевое-NN`, где `NN` — номер
раздела ниже. Метка стоит ровно там, где живёт отличие: в комментарии кода, а
если в файле комментарий невозможен (`package.json`) или файл менять нельзя
(`.gitlab-ci.yml`, `tools/sync-github` — только по просьбе оператора), — в
README или документе рядом.

```sh
git grep -n "#учебно-не-боевое"       # все места
git grep -n "#учебно-не-боевое-07"    # одно отличие
```

Номер раздела постоянный: новые отличия получают следующий свободный номер, а
не вставляются в середину, поэтому ссылки на номер из кода и из Issue не
устаревают. Разделы сгруппированы по темам, номера внутри групп идут не подряд.
Устранённое отличие не удаляют: заголовок получает пометку «(снято)»
(`### NN. (снято) …`), метки из кода убирают, строку «Где» и строку таблицы
оставляют с пояснением, номер не переиспользуется.

У каждого раздела есть строка **Где:** — файлы, в которых стоит его метка.
Номера, метки, строки «Где» и ссылки сводной таблицы сверяет проверка (без
сети и зависимостей, нужен только `git`):

```sh
node --test tools/docs-check/markers.test.mjs
```

Проверка смотрит рабочую копию: файлы из git и новые, ещё не добавленные, без
игнорируемых. Она падает, если:

- номер раздела повторяется или пропущен;
- у раздела нет метки ни в одном файле, или метка ссылается на несуществующий
  или снятый раздел;
- файлы в «Где» не совпадают с файлами, где стоит метка (у снятого раздела —
  проверка пропускается);
- в коде метка без номера;
- строка сводной таблицы ведёт не на свой раздел, или якорь заголовка на GitHub
  и GitLab получается разным. GitLab сжимает «--» в «-», а «--» получается из
  любого знака препинания между пробелами, поэтому в заголовках нет « — »,
  « → », « / » и двойных пробелов.

Новое отличие добавляется так: раздел со следующим номером в своей группе,
метка в коде, строка в сводной таблице.

Метки не путать с двумя другими (`AGENTS.md`):

| Метка | Что отмечает |
| --- | --- |
| `#внимание-учебно-аналитический-предохранитель` | удалить после первого разбора ограничение автоматизации ChattyMy: лимит, пауза, запрет, остановка |
| `#модельный-учебно-аналитический-контроль` | удалить после первого разбора место, где Claude сверяет, что работа не вышла за учебные рамки |
| `#учебно-не-боевое-NN` | решение, привести к боевой системе |

Предохранитель часто и есть учебное отличие: в бою его заменило бы устройство
системы (например, лимит частоты и бюджет API вместо счётчика сообщений). Тогда
у места две метки.

## Главное в одном абзаце

Учебный мост вводит текст в веб-интерфейс ChattyMy через браузер оператора и
читает ответ со страницы. 

Отличия 01–06, 14–16, 26 и 27 и почти все предохранители моста есть только
потому, что транспорт — чужой интерфейс; часть из них (04–06, 16, 26, 27) в бою
не исчезает, а меняет форму, а 15 переходит в инфраструктуру. Плагин Paseo
остаётся, а файловый протокол (07–10, 13, 25) в бою не нужен: провайдер сам
вызывает API, и лишь если исполнитель останется отдельным процессом — очередь
сообщений вместо папки. Состояние и срок хода (11, 28) и возможности провайдера
(12) решаются в самом провайдере при любом исполнителе. Песочницы, секреты и эксплуатация (17–23)
— типичные упрощения стенда на одном ноутбуке. 24 и 29 — процесс работы по
очереди в GitLab и GitHub, решение оператора.

## Транспорт к модели

### 01. Канал к модели: веб-интерфейс ChattyMy

**Где:** `tools/ChattyMy-bridge/bridge.ts`, `tools/ChattyMy-bridge/main.ts`

- **Учебно.** Мост подключается к Chrome оператора по CDP (протокол отладки
  Chrome), вводит текст в поле чата клавиатурой и ждёт ответ на странице.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Цель задачи — разобрать, как веб-ChattyMy из подписки
  встраивается в Paseo (`docs/integration-options.md`, вариант 4б); у API
  другие модели и другая оплата.


### 02. Разметка страницы как контракт

**Где:** `tools/ChattyMy-bridge/bridge.ts`, `tests/e2e/fake-ChattyMy.html`

- **Учебно.** Контракт с ChattyMy — селекторы `SEL`, снятые с живой страницы
  2026-10-06, и подписи кнопок на русском («Остановить», «Сгенерировать ответ
  заново»). Имитация в тестах повторяет ту же разметку.
- **Боевое.** реализовать после первого разбора
- **Почему так.** У веб-интерфейса нет публичного контракта; опереться можно
  только на то, что видно на странице.
- **Чем грозит.** ChattyMy меняет разметку без предупреждения, а тесты на
  имитации этого не поймают: имитация меняется только руками. Сменился язык
  интерфейса — подписи не совпадут, и отказывает сразу несколько защит:
  проверка «чат занят» перестаёт видеть идущий ответ (предохранитель молча
  пропускает), «Стоп» в Paseo и Ctrl+C не останавливают ответ в ChattyMy, а
  конец ответа не распознаётся: первый же ход через 10 минут после начала
  ответа завершается ошибкой (полный ответ остаётся только в чате ChattyMy), и
  мост останавливается.

### 03. Ответ собирается из разметки страницы

**Где:** `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** `readTurn` обходит DOM ответа и восстанавливает markdown:
  списки, таблицы, код, ссылки. Картинки пропадают целиком (вместе с подписью
  `alt`), формулы превращаются в плоский текст, блоки внутри ячеек таблиц
  склеиваются в строку. Текст не экранируется: буквальные `*`, `_`, `#` или
  `1.` в начале строки станут в Paseo разметкой.
- **Боевое.** реализовать после первого разбора
- **Почему так.** Со страницы доступна только отрисованная разметка.
- **Чем грозит.** Ответ в Paseo отличается от того, что сгенерировала модель:
  что-то пропало, что-то стало форматированием.

### 04. Сбои распознаются по косвенным признакам

**Где:** `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Лимит, капчу и ошибку мост между собой не различает. О сбое он
  узнаёт только по тому, чего на странице нет: сообщение не принято за
  2 минуты, ответ не начался, не закончился за 10 минут, пришёл пустым. На
  любой такой сбой мост пишет `error-<id>.md` (если ответ идёт, сперва жмёт
  «Остановить») и завершается с кодом 1; продолжить — перезапуск человеком.
  Ошибку после части ответа он не отличает от конца ответа (README моста,
  «Известные ограничения»).
- **Боевое.** реализовать после первого разбора.
- **Почему так.** После Enter повторять нельзя по двум причинам: повтор —
  второе сообщение в чате (06), а повтор после лимита или капчи — обход
  ограничений, который запрещают условия OpenAI. До Enter мост повторяет
  только ввод текста в поле. Остановиться и позвать человека — единственное
  честное действие.
- **Чем грозит.** Обрезанный ответ может уйти в Paseo как полный; каждый сбой
  требует ручного перезапуска.

### 05. Лимиты и паузы: константы на запуск

**Где:** `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Не больше 20 сообщений за запуск (явно — до 500) и не чаще
  одного в 20 секунд. Считает каждый мост сам, в памяти процесса; два моста на
  разных каталогах считают раздельно. Длина сообщения и ответа не
  учитывается.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Цель лимита здесь — не нагрузка, а рабочие рамки
- **Чем грозит.** Лимит обходится любым перезапуском: счётчик живёт в памяти,
  новый запуск — снова до 20 сообщений (с `--limit` — до 500). Паузу
  перезапуск не обходит: запуск считается отправкой. Защита держится на
  дисциплине и на чек-листе (21).

### 06. «Не больше одного раза» с ручной сверкой

**Где:** `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Мост помнит отправленное в памяти (`sentIds`) и никогда не
  повторяет Enter. Если мост упал посреди хода, сообщение могло уйти, а могло
  и нет: мост отказывается отправлять такую задачу, а человек открывает чат и
  проверяет глазами.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Чат ChattyMy — внешнее состояние, которое нельзя ни
  откатить, ни спросить «было ли это сообщение».
- **Чем грозит.** После падения ход нужно разбирать вручную.

### 26. Контекст модели: общий чат, а не сессия Paseo

**Где:** `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Мост берёт задачи из всех папок сессий и отправляет их в один
  открытый чат. В задаче — только последнее сообщение; что ещё видит модель,
  решает переписка в чате. Отменённые и упавшие ходы остаются в ней: «Стоп»
  оставляет сообщение и часть ответа, сбой после Enter — сообщение.
- **Боевое.** реализовать после первого разбора
- **Почему так.** Мост привязан к одному существующему чату и новых не
  открывает (предохранитель).
- **Чем грозит.** Ответ одной сессии строится с учётом сообщений другой;
  модель продолжает разговор, который в Paseo отменён. История Paseo и
  контекст модели расходятся.

### 27. Модель и параметры выбирает интерфейс

**Где:** `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Модель — та, что выбрана в чате, или та, на которую ChattyMy
  переключил сам (например, по лимитам подписки). Параметры генерации задать
  нельзя. Ни журнал моста, ни Paseo модель не записывают: в Paseo она всегда
  называется `ChattyMy`.
- **Боевое.** реализовать после первого разбора
- **Чем грозит.** Прогон невоспроизводим: ответы одного прогона могут дать
  разные модели. Поэтому модель чата оператор записывает в ноту прогона
  (чек-лист в README моста).

## Плагин Paseo и протокол обмена

### 07. Файловый «почтовый ящик» вместо очереди

**Где:** `tools/paseo-plugin/server/protocol.ts`

- **Учебно.** Плагин и мост обмениваются файлами в `.ai-bridge/paseo/<сессия>/`:
  `task-`, `claim-`, `reply-`, `error-<id>`. Протокол v2 — один модуль на обе
  стороны. Папка лежит внутри рабочего дерева git агента, и `.gitignore` для
  неё плагин не создаёт.
- **Боевое.** реализовать после первого разбора
- **Почему так.** Файлы видны глазами, их можно написать руками
  (`echo "Ответ" > reply-<id>.md`), они не требуют инфраструктуры и доступны
  обеим сторонам — на Маке и в контейнере через общий том (с оговорками
  08–10). Это лучший формат для разбора протокола.
- **Чем грозит.** Нет гарантий доставки, порядка и ограничения по размеру;
  работает только на одной машине с общей папкой. Переписка с ChattyMy может
  попасть в коммит (`git add -A`), а `git clean -fdx` или `git stash -u`
  удаляют живые файлы протокола вместе с замком `.bridge.lock`: плагин
  завершает ход ошибкой «файл задачи удалён», а мост на ближайшем опросе падает
  с «замок моста потерян» и идущий ответ в ChattyMy не останавливает.

### 08. Аренда по времени файла

**Где:** `tools/paseo-plugin/server/protocol.ts`

- **Учебно.** «Жив ли владелец» — по mtime файла, срок 30 с. Плагин
  пульсирует файл задачи раз в 5 с; мост — свой захват задачи и замок моста на
  каждом опросе, раз в секунду, и на каждом пульсе сверяет свой токен в файле.
  Захват — создание файла с `O_EXCL`. Если два моста одновременно перехватывают
  брошенный замок, один может снять свежий замок другого; это ловит сверка
  токена. Перехваченный захват задачи мост не отправляет вовсе: упавший мост
  мог успеть её отправить.
- **Боевое.** реализовать после первого разбора.
- **Чем грозит.** Зависимость от часов и точности mtime на томах Docker;
  узкое окно гонки при одновременном старте двух мостов.

### 09. Долговечность записи «по возможности»

**Где:** `tools/paseo-plugin/server/protocol.ts`

- **Учебно.** Запись атомарна (временный файл, `fsync`, `rename`), но `fsync`
  папки — по возможности: часть ФС (virtiofs, тома Docker) его не умеет, и
  ошибка молча пропускается. Журнал моста дописывается без `fsync` (20).
- **Боевое.** реализовать после первого разбора
- **Почему так.** Стенд — ноутбук: при сбое питания вместе с файлами теряется
  и сам ход (11), поэтому гарантии записи сверх этого ничего не дают.
- **Чем грозит.** После аварии могут пропасть последние файлы протокола и
  последние строки журнала моста, поэтому сверка прогона по журналу (21) после
  аварии неполна.

### 10. Опрос вместо уведомлений

**Где:** `tools/paseo-plugin/server/provider.ts`, `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Плагин опрашивает папку, мост — папку и страницу, раз в
  секунду. Каждая сторона принимает результат после двух одинаковых чтений
  подряд, поэтому от конца ответа в ChattyMy до Paseo проходит до четырёх
  периодов опроса.
- **Боевое.** События: подписка на очередь, поток ответа модели (streaming).
  Задержка — доли секунды, холостой нагрузки нет.
- **Почему так.** реализовать после первого разбора.
- **Чем грозит.** Лишняя задержка и холостые чтения диска; при многих сессиях
  опрос не масштабируется.

### 11. Состояние хода только в памяти

**Где:** `tools/paseo-plugin/server/provider.ts`

- **Учебно.** Активный ход живёт в памяти процесса плагина. Перезапуск демона
  Paseo или перезагрузка плагина теряет любой ход, который ждал ответа: новый
  процесс про его id ничего не знает.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Ход короткий, человек рядом; восстановление удвоило бы
  плагин.
- **Чем грозит.** Если мост уже отправил сообщение, ChattyMy ответит, мост
  запишет `reply-<id>.md` и «ответ отдан» в журнал, но в Paseo ответа не будет.
  Повторная отправка из Paseo — второе сообщение в ChattyMy: сначала сверить
  чат (06).

### 12. Один ход за раз, только текст

**Где:** `tools/paseo-plugin/server/provider.ts`

- **Учебно.** В сессии одна задача за раз; сообщение во время хода
  отклоняется (steer не поддержан). Из сообщения берутся только части
  `type: "text"` — введённый текст и текстовые вложения (их текст вклеивается в
  задачу без заголовка и источника). Остальные вложения (загруженный файл,
  ревью, задача и MR из forge, PR и Issue GitHub) молча отбрасываются, ход идёт
  без них. Картинки отклоняются явно: плагин не объявляет `prompt.image`, и его
  `send()` (через `requireProviderCapabilities` из SDK) отвечает ошибкой.
  Сообщение только из отбрасываемых вложений (без текста и картинок) уходит
  пустой задачей.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Мост всё равно работает с одним чатом последовательно;
  параллельность ничего бы не дала, а протокол усложнила бы.
- **Чем грозит.** Ответ без учёта вложения, о котором пользователь не знает;
  пустая задача — ошибка «пустая задача» у моста.

### 13. Граница доверия: общая рабочая папка

**Где:** `tools/paseo-plugin/server/protocol.ts`, `tools/paseo-plugin/server/provider.ts`, `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** В режиме codexpro ChattyMy сам пишет в рабочую папку — ту же, где
  лежат файлы протокола. Защита — гигиена файлов: сам файл протокола читается
  без перехода по ссылке (`O_NOFOLLOW`), заменяется атомарно, FIFO и не-файлы
  отвергаются. Но только последний компонент пути: мост один раз при запуске
  проверяет, что корень `paseo` не ссылка (иначе не запускается), и пропускает
  папки сессий-ссылки; `.ai-bridge` и путь выше не проверяет никто (`main.ts`
  ещё и создаёт корень через ссылку), а плагин проходит по ссылкам при `mkdir`,
  уборке и удалении папки сессии. Кто
  написал `task-` или `reply-<id>.md`, не проверяется. Мост и codexpro-sandbox
  одновременно не работают; сам мост проверяет это только при своём запуске
  (14), в остальное время правило держат ручные проверки и люди (18).
- **Боевое.** Канал управления отделён от данных: протокол — в каталоге или
  очереди, куда модель доступа не имеет; разные учётные записи ОС; сообщения
  подписаны (HMAC) и проверяются получателем. Если файлы всё же нужны — разбор
  пути без ссылок (`openat2` с `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS`) или
  работа от дескриптора каталога.
- **Почему так.** Учебная цель — увидеть, какие атаки возможны через общую
  папку и как их гасить на уровне файлов.
- **Чем грозит.** В режиме codexpro ChattyMy может ответить или завершить
  ошибкой ход любой сессии, удалить или подменить файлы задач, а подменив
  каталог ссылкой — заставить плагин писать и удалять файлы протокола вне
  `/workspace`; подменённый `.ai-bridge` уводит туда же и мост. Подложенную задачу мост отправит в ChattyMy от имени оператора,
  если она появилась после снимка очереди при запуске. Считать ли переписку
  каналом управления агентами — решение оператора (ai/codexpro#2, README
  моста).

### 25. Конец ответа по паузе в записи

**Где:** `tools/paseo-plugin/server/provider.ts`

- **Учебно.** Плагин принимает `reply-<id>.md`, если файл не менялся между
  двумя опросами (1 с). Пустой ответ не принимается никогда.
- **Боевое.** реализовать после первого разбора.
- **Чем грозит.** Писатель, замерший дольше секунды посреди записи, отдаст в
  Paseo обрезанный ответ как полный; плагин тут же удалит файлы хода, и
  дописанное потеряется. Пустой ответ вешает ход (28).

### 28. Ход без срока

**Где:** `tools/paseo-plugin/server/provider.ts`

- **Учебно.** Плагин ждёт ответа сколько угодно и на захват моста не
  смотрит. Мост упал после захвата — ответа не будет, а Paseo показывает
  идущий ход, пока человек не нажмёт «Стоп»; о падении исполнителя плагин не
  сообщает.
- **Боевое.** реализовать после первого разбора
- **Почему так.** Ответ может написать человек в любой момент, и срок для
  него не задать.
- **Чем грозит.** Зависший ход в Paseo; что сообщение могло уйти в ChattyMy,
  человек должен догадаться сам (README моста, «Падение моста»).

## Песочницы, сеть и секреты

### 14. CDP без пароля и проверка Chrome по `ps`

**Где:** `tools/ChattyMy-bridge/cli.ts`, `tools/ChattyMy-bridge/main.ts`, `tools/codexpro-sandbox/README.md`

- **Учебно.** CDP Chrome открыт на `127.0.0.1:9222` без пароля, и до него
  достают контейнеры и машины OrbStack. «Тот ли это Chrome» мост решает по
  командной строке процесса из `lsof` и `ps`; сомнение — отказ. «Кто ещё
  рядом» — по списку контейнеров `docker` и машин `orb list`: отказ вызывают
  только неостановленный codexpro-sandbox и сбой docker, остальное лишь
  пишется в журнал. Сбой `orb list` отказа не вызывает и пишется как «не удалось
  узнать», а незнакомый вывод журнал записывает как «машины OrbStack — нет»:
  машины сверяют с `orb list` руками. Разбор `orb list` — прямо в `main.ts`, без
  тестов.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Стенд — ноутбук оператора; отдельная машина ради редких
  прогонов не окупается.
- **Чем грозит.** Этим Chrome со входом в ChattyMy может управлять любой
  локальный процесс Мака, любой контейнер и любая машина OrbStack — в том
  числе скрипты установки npm-пакетов. Разбор `ps` — эвристика, а не
  доказательство.

### 15. Сеть проверяется один раз при запуске

**Где:** `tools/ChattyMy-bridge/main.ts`

- **Учебно.** Мост спрашивает mihomo, стоит ли группа `FOREIGN` на
  `FOREIGN_STRICT`, и проверяет флаг прокси у Chrome — один раз, до
  подключения. Проверяются настройки, а не фактический маршрут: что порт
  17891 ведёт в группу `FOREIGN` — допущение из `AGENTS.md`, а расширения и
  политики Chrome (у них приоритет выше флага) и WebRTC могут ходить мимо
  прокси.
- **Боевое.** Маршрут закреплён инфраструктурой: исходящий трафик сервиса
  выпускает только сетевая политика или шлюз, и другого пути нет. Приложение
  не проверяет сеть — оно не может её обойти.
- **Почему так.** Прокси — настройка рабочего Мака оператора, а не
  инфраструктура проекта (`AGENTS.md`).
- **Чем грозит.** Разрыв между проверкой и использованием (TOCTOU): смену
  выхода во время прогона мост не заметит. Обход прокси мимо флага проверка не
  видит вовсе.

### 16. Личный аккаунт оператора

**Где:** `tools/ChattyMy-bridge/main.ts`, `tools/ChattyMy-bridge/README.md`, `tools/codexpro-sandbox/README.md`

- **Учебно.** Мост работает от имени основного аккаунта ChattyMy оператора — с
  его памятью, историей и подключёнными коннекторами (в том числе боевым
  `CodexPro`). Через `codexpro-sandbox` тот же аккаунт читает всю рабочую
  папку `/workspace`: её файлы уходят в OpenAI на условиях личной подписки.
  Защита — чек-лист: в чате прогона выключить все коннекторы, память
  выключить или принять осознанно, ничего чувствительного в сообщениях; мост
  этого не проверяет.
- **Боевое.** реализовать после первого разбора
- **Почему так.** Задача — именно веб-ChattyMy из подписки оператора (01).
- **Чем грозит.** В ответ может попасть личное из памяти ChattyMy; ошибка
  оператора открывает модели боевой коннектор.

### 17. Секреты в файлах, переменных и URL

**Где:** `tools/codexpro-sandbox/README.md`, `tools/paseo-sandbox/README.md`, `tests/e2e/paseo.spec.ts`

- **Учебно.** Токен codexpro — в файле на томе и в URL туннеля
  (`?codexpro_token=`); этот URL вставлен в настройки коннектора ChattyMy, то
  есть токен лежит и у OpenAI. Туннель — временный `trycloudflare.com`. Демон
  Paseo — по http на `127.0.0.1:6790`, вход по одному общему паролю из
  `paseo.env` (0600); тест читает его из того же файла. Через `--env-file`
  пароль попадает в окружение контейнера и виден в `docker inspect`. Оба
  секрета созданы один раз и не ротируются.
- **Боевое.** реализовать после первого разбора
- **Почему так.** Всё живёт на одном ноутбуке. Токен — в URL, потому что
  коннектор ChattyMy настроен без аутентификации (Authentication: None), хотя
  сервер codexpro принимает и заголовок `Authorization: Bearer`.
- **Чем грозит.** Токен в URL оседает в логах контейнера, буфере обмена,
  настройках коннектора у OpenAI и журналах запросов; кто видит логи
  контейнера или `docker inspect`, видит и секреты, а они не меняются.

### 18. Изоляция и образы песочниц

**Где:** `tools/codexpro-sandbox/Dockerfile`, `tools/codexpro-sandbox/README.md`, `tools/paseo-sandbox/README.md`

- **Учебно.** Файловые инструменты ChattyMy в `codexpro-sandbox` видят только
  `/workspace`, но в контейнере на запись примонтирован и том `~/.codexpro` с
  токеном и cloudflared — под тем же пользователем `node`, под которым
  `bash safe` выполняет команды ChattyMy. cloudflared в образ не входит:
  codexpro скачивает его на этот том при первом старте, если его там нет
  (версия закреплена в codexpro, SHA-256 сверяется при скачивании); уже лежащий
  файл проверяется только запуском `--version`. По сети контейнер достаёт до
  всех сервисов Мака на `127.0.0.1`; лимитов CPU, памяти и процессов нет.
  `paseo-sandbox` тоже видит сервисы Мака, в том числе CDP Chrome (проверено),
  и работает одновременно с Chrome; от управления Chrome её защищает только
  правило «не заводить агентов, выполняющих команды». Образы — по тегу
  (`node:22-slim`, `ghcr.io/getpaseo/paseo:0.11.0-beta.5`), пакеты `apt` без
  версий, транзитивные зависимости codexpro разрешаются при каждой сборке
  (глобальная установка без lock-файла).
- **Боевое.** реализовать после первого разбора
- **Почему так.** OrbStack на Маке не даёт простой сетевой изоляции от хоста.
  Риск для CDP снижен правилом «не запускать codexpro-sandbox вместе с Chrome с
  CDP». Проверяют его в отдельные моменты: человек перед запуском Chrome
  (`docker --context orbstack inspect`), мост при своём запуске (по имени
  контейнера в контексте `orbstack`) и человек командой `curl` перед
  `docker start`; между этими моментами правило держится только на людях.
  Доступ к остальным сервисам Мака не закрыт ничем.
- **Чем грозит.** `codexpro-sandbox`, запущенный после старта моста или при
  открытом Chrome без моста, получает CDP Chrome со входом в ChattyMy (тот же
  разрыв, что в 15). Код из `bash safe` может прочитать токен и подменить
  cloudflared, и подмена переживёт перезапуск и пересборку образа: файл на томе
  codexpro заново не скачивает. Пересборка даёт другие версии пакетов.

## Эксплуатация и процесс

### 19. Запуск вручную, пути в коде

**Где:** `tools/ChattyMy-bridge/main.ts`, `tools/ChattyMy-bridge/cli.ts`

- **Учебно.** Мост запускает человек из терминала. Пути
  (`~/work/ai/codexpro/2`, сокет mihomo), порты (9222, 17891) и контекст
  `docker` записаны в коде; путь стенда записан и в тесте `paseo` (22).
- **Боевое.** Сервис под супервизором (systemd, Kubernetes) с проверками
  здоровья; конфигурация — из переменных окружения или файла, проверяется
  схемой при старте; одинаковый артефакт на всех окружениях.
- **Почему так.** «Только вручную» — сам по себе предохранитель (ai/codexpro#2,
  п. 6): у моста нарочно нет демона и расписания. Стенд один, настраивать
  нечего.
- **Чем грозит.** Перенос на другую машину требует правки кода.

### 20. Журнал: текстовый файл

**Где:** `tools/ChattyMy-bridge/main.ts`

- **Учебно.** Строки «время UTC + событие» дописываются в `bridge-runs.log`
  (`appendFileSync`, без `fsync`); прогон сверяют глазами по чек-листу. Текстов
  задач и ответов в журнале нет.
- **Боевое.** Структурные логи (JSON) с идентификатором хода во всех строках,
  сбор в централизованное хранилище; метрики (отправлено, время ответа,
  ошибки), трассировка от сообщения в Paseo до ответа модели; алерты по
  порогам; журнал аудита, который нельзя исправить задним числом.
- **Почему так.** Прогонов единицы, читатель — оператор и Claude.
- **Чем грозит.** Журнал можно отредактировать, а после аварии в нём может не
  хватать последних строк (09); по нему не построить статистику и не получить
  сигнал о сбое без человека.

### 21. Контроль рамок: чек-лист и нота

**Где:** `tools/ChattyMy-bridge/README.md`, `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Что прогон не вышел за учебные рамки, проверяют оператор и Claude
  по чек-листу «Живой прогон»; разрешение и итог — ноты в Issue. Часть пунктов
  мост проверяет сам и без них не стартует: codexpro-sandbox остановлен,
  профиль и прокси Chrome, одна вкладка в чате `/c/…`, пустая очередь.
- **Боевое.** реализовать после первого разбора.
- **Почему так.** Этот контроль — учебный материал сам по себе: ученики
  разбирают, что машина проверить может, а что остаётся человеку.
- **Чем грозит.** Пункты, которые мост не проверяет (слово оператора на
  прогон; что чат новый и отдельный — мост видит только адрес `/c/…`;
  содержание сообщений; коннекторы и память ChattyMy; модель чата; прочие
  контейнеры и машины; агенты в `paseo-sandbox`; `--limit` по числу сообщений;
  все проверки после прогона), держатся только на людях: пропущенный такой пункт ничего не
  остановит.

### 22. Тесты на имитации и живом стенде, без CI

**Где:** `tests/e2e/playwright.config.ts`, `tests/e2e/paseo.spec.ts`, `tools/ChattyMy-bridge/bridge.ts`

- **Учебно.** Мост тестируется против имитации `fake-ChattyMy.html`, которая
  повторяет разметку на дату замера (02). Тест `paseo` работает на живом стенде
  оператора: та же папка `.ai-bridge/paseo`, что у настоящего моста и у
  `codexpro-sandbox`, путь записан в коде; от смешения с живыми ходами
  защищают проверки в самом тесте, задачи и агенты прошлых прогонов остаются.
  В CI тестов нет: задание `smoke` печатает `smoke ok`, тесты гоняют руками.
  Ядро моста принимает параметры только для тестов — `pauseMs` меньше 20 с,
  `acceptQueued`, сроки `startTimeoutMs` и `answerTimeoutMs`, `leaseMs`,
  `pollMs`, `retries`; границы ядро проверяет только у `limit`.
- **Боевое.** Все тесты — в CI на каждый MR, обязательные для слияния;
  одноразовое окружение на прогон (свой демон, временные тома); у API
  поставщика нет песочницы, поэтому контракт проверяют записанными ответами
  (record/replay) в обычных тестах и редкими тестами против настоящего API на
  отдельном проекте с малым лимитом расходов. Нужное для тестов подставляется
  зависимостями (часы, источник задач), а не параметрами рабочего интерфейса.
- **Почему так.** Живой ChattyMy в CI запускать нельзя (01), а раннер проекта —
  общий shell-раннер; `.gitlab-ci.yml` меняется только по просьбе оператора.
- **Чем грозит.** Регрессию заметят только при ручном прогоне. Тестовые
  параметры ядра можно передать и не в тесте: например, `answerTimeoutMs:
  Infinity` выключает предохранитель «не закончил за 10 минут» — держит только
  соглашение.

### 23. Сборка и поставка

**Где:** `tools/paseo-plugin/README.md`, `tools/paseo-sandbox/README.md`, `tools/ChattyMy-bridge/README.md`

- **Учебно.** TypeScript исполняется напрямую (`node main.ts`, плагин — как
  исходники), без сборки. Плагин копируется в песочницу `rsync`, версия
  `0.0.0`. Paseo — beta `0.11.0-beta.5`. SDK Paseo и `playwright-core`
  закреплены точно, остальные зависимости — с `^`, их точные версии держит
  только `package-lock.json`. Мост, тесты и проверку меток исполняет Node с
  Мака оператора; версия не закреплена (нет `engines` и `.nvmrc`), а
  `node main.ts` без сборки требует Node со снятием типов по умолчанию — 22.18+
  или 23.6+.
- **Боевое.** Сборка в CI, версия рантайма закреплена (`engines`, `.nvmrc`,
  образ по дайджесту) и одна в CI и на стенде, версионированный подписанный артефакт, список
  компонентов (SBOM), выкладка тем же артефактом на все окружения, откат на
  прошлую версию; стабильные релизы зависимостей и автоматические обновления
  с проверкой (Renovate, Dependabot).
- **Почему так.** Учебный цикл «поправил — перезагрузил плагин» должен быть
  коротким, а Paseo с провайдерами-плагинами пока есть только в beta.
- **Чем грозит.** Что именно работает в песочнице, знает только тот, кто
  копировал: мост берёт протокол из рабочей копии, плагин — из копии `rsync`,
  и после правки протокола без `rsync` и `paseo plugin reload` стороны
  разойдутся. Beta Paseo может сломать API плагинов. На другой машине или после
  обновления Node мост и тесты идут на другом рантайме, а на старом не
  запускаются вовс

  `api`. Задание с защищёнными переменными идёт на общем shell-раннере
  `vm124-shell`, где выполняются и задания MR: у shell-исполнителя общий
  пользователь, поэтому задание из MR может оставить подмену `git` или правку
  `~/.gitconfig`, и следующая синхронизация отдаст токены ей. К GitLab токен
  идёт по http внутри локальной сети.
- **Боевое.** GitHub App с короткоживущими токенами установки или токен на один
  репозиторий; бот GitLab с минимальной ролью и `write_repository`, заметку
  пишет отдельный токен; отдельный изолированный раннер для заданий с
  секретами; TLS до GitLab; срок токенов отслеживает система, а не запись в
  документе.
- **Почему так.** Один оператор, один раннер и решение оператора про токен на
  все репозитории (нота в ai/codexpro#4).
- **Чем грозит.** Утечка с общего раннера даёт права мейнтейнера проекта и
  запись во все репозитории `dinered`. Кто может писать в `main` на GitHub
  (люди, сессии агентов, обладатель утёкшего PAT), тот правкой `sync.sh` или
  `.gitlab-ci.yml` получает токены синхронизации: задание само принесёт правку
  и исполнит её (24) — это «отравление пайплайна» (poisoned pipeline
  execution).

## Что уже сделано по-боевому

Не всё в учебном коде упрощено. Эти решения переносятся в боевую систему как
есть, и на них стоит смотреть как на образец (с оговорками в скобках):

- **Атомарная запись** (`writeAtomic`): временный файл, `fsync`, `rename` —
  читатель видит файл целиком или не видит вовсе.
- **Гигиена файлов**: чтение без перехода по ссылкам, отказ от FIFO, создание
  с `O_EXCL`. Те же приёмы нужны любому сервису, который читает файлы из чужой
  папки (для всего пути, а не только последнего компонента, — 13).
- **Отказ по умолчанию**: при неясности (docker не ответил, `ps`
  неоднозначен, очередь не пуста) мост не запускается. Исключение — `orb list`:
  его сбой только пишется в журнал, а незнакомый вывод выглядит как «машин нет»
  (14).
- **Один модуль протокола на обе стороны**: в исходниках формат один для
  плагина и моста (в песочнице плагин — копия, 23).
- **Чистые функции решений** (`cli.ts`): проверки Chrome, контейнеров, реакция
  на сигналы и строка журнала тестируются без docker, Chrome и терминала.
  Проверка `FOREIGN_STRICT` и разбор `orb list` пока в `main.ts`, без тестов.
- **Тесты на граничные случаи**: ссылки, падения моста, сон Мака, второй мост,
  удаление файла между проверкой и пульсом воспроизводятся в тестах (мост — на
  имитации ChattyMy, протокол — на файлах); решение по повторному сигналу
  проверено как чистая функция. Гонка двойного перехвата (08) тестом не
  воспроизведена.
- **Наши скрипты секреты не печатают**: токен и пароль создаются сразу в файл
  0600, на экран не выводятся. Исключение — сам codexpro: он печатает токен в
  лог контейнера (17). Буфер обмена, через который их передают, — учебный
  компромисс.
