# Соглашение о совместной работе

Репозиторий: `dinered/codexpro` · Редакция от 2026-10-25
Участники: владелец репозитория и AI-агент (Z.ai).

## 1. Цель и рамки

Совместная разработка эталонной реализации моста (protocol v3), деплой-инфраструктуры и учебного курса по анти-бот-защитам. Агент работает только в рамках задач, поставленных владельцем; новые крупные направления — после согласования в чате. Решения о мерже, релизах и изменении инфраструктуры принимает владелец.

## 2. Принципы

- **Безопасность прежде всего.** Всё, что касается взаимодействия с платформами, — только детекция сопротивления и остановка (П-6). Обход защит, маскировка и «адаптация к блокировкам» — вне рамок работы.
- **Ничего не ломаем.** Изменения кода сопровождаются контрактными тестами; перед пушем — полный прогон. Без фиксированных цифр: в каждом PR указываются точная проверенная голова (SHA), фактические команды и фактический результат прогона.
- **Прозрачность.** Агент ведёт локальный worklog и отчитывается в чат; скрытых изменений нет. Каждый PR содержит описание «что / зачем / как проверено».

## 3. Ветки и коммиты

- Имена веток: `fm/<тема>-<дата>`, например `fm/bridge-reference-update-20261025`.
- Base — свежий `origin/main`; перед началом работы обязательный `fetch`.
- Коммиты атомарные, сообщения краткие и по существу.
- Force-push и перезапись опубликованной истории — запрещены.

## 4. Pull Requests

- Каждое изменение — отдельная ветка и PR. Код-фиксы и связанная с ними документация/тесты могут ехать в одном PR; независимые организационные изменения (как это соглашение) — отдельно.
- Мерж только после одобрения владельца; мелкая документация может мержиться без длинного ревью.
- Если PR решает ишью — ссылка на #N в описании.
- В описании PR — точная проверенная голова, фактические команды проверки и их результат.

## 5. Issues

- Задачи и улучшения фиксируются ишью (создание через GitHub API).
- Формат текста: проблема → предложение → приёмка; приоритет указан явно.
- Статус работы по ишью отражается ссылками из коммитов и PR.

## 5.1. Площадки и исполнители

- GitHub — рабочая площадка коллег: ветки, PR, ишью и обсуждения живут здесь.
- Существующие копии в GitLab — для сверки. Номера ишью на площадках независимы — в переписке и документах нужны полные ссылки, а не голые номера.
- Одна задача — один исходный исполнитель. Перенос веток между площадками не означает перенос PR, ишью и обсуждений.

## 6. Доступы и секреты

- Авторизация описывается через существующие согласованные средства и не требует замены текущего входа владельца на deploy-ключ/PAT.
- Запись агента в репо — SSH deploy-ключ (только git-протокол, без REST API); API-доступ агента — fine-grained PAT с минимальными правами и коротким сроком жизни; хранится вне репозитория (права `600`), в коде, коммитах и issue-текстах не фигурирует.
- Секреты, токены и пароли в репозиторий не попадают — ни при каких обстоятельствах.
- Выдача новых доступов, отзыв и перевыпуск credentials — решения владельца, принимаются вне чата.

## 7. Прод

- Merge меняет исходники для будущей сборки; замена работающего контейнера — отдельное развёртывание с проверкой образа, конфигурации и сохранности состояния. Текущий `.gitlab-ci.yml` содержит smoke/sync-проверки, а не автоматический rollout.
- Сборка образа исходит из снапшота эталона (`docs/mydocs/z.ai/download/bridge-reference`, Dockerfile `COPY`) и применяет deployment-патчи; поэтому PR, меняющий снапшот, всегда проходит полный тестовый прогон и ревью владельца, а pins/checksums в Dockerfile обновляются в том же PR.
- Полномочия на merge и развёртывание — у владельца, включая исполнение конкретных заранее данных распоряжений. Мерж в `main` выполняет владелец.
